**This upgrade is free for everyone.** You never need a current subscription to run the latest version of Cerb, and there's nothing to renew before upgrading. Cerb Cloud subscribers will be upgraded automatically.

# Important Release Notes

- [**Always make a backup before upgrading!**](/docs/backups/)

- **Cerb 12.0** requires **PHP 8.5+** and **MySQL 8.0+** (or **MariaDB 10.5+**).

- To upgrade your installation, [follow these instructions](/docs/upgrading/).

## Added

### Licensing

- **[Setup/Licensing]** **Self-hosted Cerb is now free, with unlimited workers and unlimited seats.** Cerb has always been free to self-host, but Community Edition allowed only a single simultaneous worker login, and that limit is gone – there's no seat enforcement anywhere, and no worker is displaced to make room for another. What a license raises instead, at **Setup » Configure » Subscription**, is **concurrency**: how much background work and how many AI agent turns your installation can run at once. Every install, licensed or not, gets a floor of three concurrency slots, and a license carrying fewer than three grants three. A license removes the ceiling on that pool – a licensed installation sets its own slot count on **Setup » Configure » [Queues](/docs/setup/configure/queues/)** – and unlocks [lane configuration](/docs/setup/configure/queues/), so the pool can be divided between batch work and agent turns rather than following a fixed formula. A license also raises how many agent turns a single slot carries at once, from two to six – an agent turn spends nearly all of its life waiting on a model provider, so that multiplier is most of what a busy install feels. Licensed-only plugins will join that list by release. An expired license drops concurrency back to the community floor – three slots and the default lane split, with a stored split preserved and reapplied if the subscription returns – while every feature keeps working and workers and seats stay unlimited, so lapsed coverage slows an installation down rather than locking anyone out.

### AI agents

https://www.youtube.com/embed/TPSTDjX6Unw

- **[Agents]** Added **[AI workers](/docs/agents/)**. An agent is an ordinary [worker](/docs/workers/) record with an `is_ai` flag rather than a separate record type, so it can own tickets, be `@mentioned`, join groups, and hold API credentials like anyone else. An AI worker never has an interactive session (logins and SSO are refused), and doesn't require an email address.

- **[Agent Models/LLMs]** Added **[Agent Model](/docs/records/types/agent_model/)** records for configuring the LLM models available to automations and agents. A model record holds its provider, model ID, optional API endpoint URL, an encrypted [connected account](/docs/records/types/connected_account/) for credentials, its context window, a display icon and color, and a block of provider-specific parameters. It also carries an availability status – **Available**, **Unlisted**, or **Disabled** – and a `priority`. Unlisted is the state for a model you want reachable by name without it turning up wherever something asks for "a model", and priority is the order models are offered in when nothing names one. Automations reference a model by name instead of repeating a provider block inline, so credentials and tuning live in one place. Because the endpoint is overridable, an OpenAI-compatible provider entry can point at a self-hosted or proxied server, which is how a locally served model is configured. A `Test` button sends one short message to verify the credentials and model string before the record is used.

- **[Agent Models/LLMs]** The model ID field on an [agent model](/docs/records/types/agent_model/) record autocompletes. It starts from the IDs shipped with each provider, and a `Refresh` button replaces those with your own account's catalog – fetched live from the provider using the credentials in the form, so it works before the record has ever been saved. The field stays free text either way, so a model ID works the day it ships whether or not it's in a list. Picking a model fills in the record's name, along with its context window and image support wherever the provider publishes them, and shows the provider's own description of it as a hint. A refresh that fails says why, reporting the provider's own error rather than quietly falling back to the shipped list.

- **[LLM/Agent Models]** [Agent models](/docs/records/types/agent_model/) now record what they can do and how they compare, so an [automation](/docs/automations/) can describe the model it needs instead of naming one. The idea is one line: hard requirements belong to the pool, and best-effort preferences belong to the caller. A model that can't accept images isn't eligible at all, because sending it one is an error; asking a model to think harder costs nothing on a model that thinks less.

- **[LLM/Agent Models]** An [agent model](/docs/records/types/agent_model/)'s ratings draw as meters wherever they appear, with one color per rating so you can tell them apart without reading the labels: intelligence is purple, speed is orange, privacy is blue, and cost is green. Cost reads as money rather than as a score because it's the one rating where a higher tier is worse. You'll see them on the agent model worklist, profile, and card, matching the [agent prompt](/docs/automations/triggers/interaction.worker/elements/agentPrompt/)'s model picker, and the model editor keeps its glyphs tinted to the same colors. Each meter names its tier in a tooltip. The worklist shows all four ratings by default, since four compact meters fit where four words don't. Tier names are capitalized for display only, so `ZDR` reads as an acronym while search queries and bulk updates use the lowercase `zdr` you type.

- **[LLM/Agent Models]** The [`agentPrompt`](/docs/automations/triggers/interaction.worker/elements/agentPrompt/) model picker now shows what each model can do and how it compares, so the choice is informed before it's made. Picking a model used to mean reading a list of names: everything that would inform the choice – whether it can see an image, whether it thinks, how capable or fast or private or expensive it is – lived on the model record, one navigation away from the moment you were deciding.

- **[Agents/Models]** The pool of [agent models](/docs/records/types/agent_model/) an automation may use is resolved by **searching** them rather than from a hand-maintained list. Adding a model puts it in every pool it qualifies for with no edit anywhere, and a pool can ask about anything a model records – its capabilities, its ratings, its context window, or your own custom fields. This is the resolver the [`llm.router:`](/docs/automations/commands/llm.router/) command and the implicit default are both built on. A search can only ever _narrow_ a pool: unlisted and disabled models are excluded before the caller's search is applied, and each model's status is re-checked on every resolve, so unlisting a model takes it out of every pool immediately. That's what makes it safe to let an [automation](/docs/automations/) write one. Omit a search entirely and you get every available model, in the `priority` order an admin set.

- **[Automations/LLM]** In [automations](/docs/automations/), added the [`llm.router:`](/docs/automations/commands/llm.router/) command. It resolves one or more [agent model](/docs/records/types/agent_model/) searches to a list of models a script can work with as data – to round-robin them, weight them by cost, skip one that's over a rate or spend budget, balance across credentials, or feed two commands from a single resolution. Nothing names a model and nothing names a router record, so a shared automation asks for what the _work_ needs rather than for something that has to already exist on the installation it's running on.

- **[Automations/Agents]** The [`llm.agent:`](/docs/automations/commands/llm.agent/) command takes an optional `agent:` input naming the AI worker a turn runs as. The transcript picks up that worker's name and image, and the conversation uses that agent's memory and credentials. An agent is **identity, not model policy** – naming one says who the work is attributed to, never what it may run, so the same agent can do cheap work and expensive work and which models a turn may use depends on the work rather than on whose name is on it. A human or disabled worker is rejected.

- **[Automations/LLM]** [`llm.chat:`](/docs/automations/commands/llm.chat/) accepts an agent model by name through `model:` instead of repeating a provider block inline. Autocompletion reads the records rather than a static list, so a newly added model appears on reload. Disabled records are excluded, since they can't be referenced.

- **[Interactions]** Added the [`agentPrompt`](/docs/automations/triggers/interaction.worker/elements/agentPrompt/) form element for [worker interactions](/docs/interactions/) – the composer a worker types into when an automation runs an agent conversation. It supports `@mention` completion for workers and filesystem files, image paste and attachment, model selection, and custom slash commands, including rewrite commands that expand in the browser before the turn is submitted.

- **[Agents]** Added **[Agent Filesystem](/docs/records/types/agent_filesystem/)** records – named volumes of [files](/docs/records/types/agent_file/) that agents and workers can both read and write. Each volume tracks its file count and total size.

- **[Agents/Automations]** Agents can [mount virtual filesystems](/docs/agents/#agent-filesystems) through a single `agent_terminal` tool. An automation lists the volumes to mount under `mounts:`, and the agent can read and write them for the rest of the conversation. Each mount can be read-only (the default) or read-write, mounted at a chosen path, and provisioned on first use. Because one tool covers every volume, the tool schema stays constant as mounts change – which keeps the cached prompt prefix intact.

- **[Agents]** [Agent filesystems](/docs/agents/#filesystem-commands) are worked with using familiar file commands: `ls`, `find`, `cd`, `read`, `search`, `write`, `append`, `edit`, `copy`, `rm`, and `pwd`. The same command set is available to an agent through its tool and to a worker through the Setup terminal, so the two can't drift. Command output can be piped through a Twig filter chain, and oversized output spools to a `/tmp` scratch area.

- **[Agents/Filesystem]** Added ZIP bulk import for agent filesystems. Upload an archive and its files are imported by a background [queue job](/docs/records/types/queue_job/), with progress shown on the filesystem record.

- **[Agents/Filesystem]** Added an 'Agent Filesystem' card widget. It shows a volume's file count and size, imports a ZIP archive, and displays a history of past imports.

- **[AI/Agents]** Where an agent chat appears is part of the [agent](/docs/agents/), not a separate list to keep in sync with it. Every [agent pane](/docs/toolbars/interactions/agent.pane/) and the command bar lists the agents enabled for _that_ surface, each with its own name and picture and a second line saying what it's for. An agent is enabled somewhere by having a block for that surface in its own configuration, so setting one up is one record rather than a record and a toolbar section that have to agree – and one shared [interaction](/docs/interactions/) serves every agent instead of being copied per agent.

- **[Interactions]** Added the [`uiCommand`](/docs/automations/triggers/interaction.worker/elements/uiCommand/) await for driving a host editor from an [interaction](/docs/interactions/). An agent chat can read and write the editor it was launched beside. A single `await:form:` can carry several commands, each gated on what the agent actually asked for.

- **[Automations/LLM]** An [`llm.agent:`](/docs/automations/commands/llm.agent/) turn can join an existing conversation. A script mints one session id and hands it to the agent, the [composer](/docs/automations/triggers/interaction.worker/elements/agentPrompt/), and the [transcript](/docs/automations/triggers/interaction.worker/elements/llmTranscript/), so all three work on the same conversation instead of the agent starting its own.

- **[Automations/LLM]** Added [transcript compaction](/docs/agents/#long-conversations) for long agent sessions. A conversation that outgrows the model's context window folds older turns behind a summary instead of failing. By default this triggers at 90% of the context window and keeps roughly the last 5% verbatim, both configurable per model under `compaction:`. A worker can also fold a session on demand with `/compact`.

- **[Automations/LLM]** Agent turns can run off-request through a [queue](/docs/queues/). A long turn survives navigating away and finishes in the background.

- **[Platform/LLM]** Added Server-Sent Event streaming for LLM turns. A long generation is no longer killed by a request timeout partway through, and a running turn can be stopped. Streaming landed first on the Anthropic provider and now covers every chat provider Cerb ships.

- **[LLM/Providers]** Added [prompt caching](/docs/agents/#long-conversations) for agent turns, on by default. A long conversation re-sends the same prefix every turn, and caching it cuts what that costs.

- **[LLM/Providers]** Added per-turn token usage accounting. What each turn consumed is recorded and shown in agent transcripts, along with the conversation's current size and session totals that separate full-price input from cached reads and writes – so it's visible at a glance whether [prompt caching](/docs/agents/#long-conversations) is actually earning its keep on a long conversation.

- **[LLM/Transcripts]** Effort level and reasoning tokens are now shown on LLM agent transcripts, alongside the per-turn token usage already reported there.

- **[LLM/Providers]** Standardized reasoning configuration on a canonical `effort:` key plus a grouped `thinking:` block. One authoring form now drives reasoning across every provider that supports it.

- **[LLM/Reasoning]** Reasoning effort now reaches every model provider, and a level you pick is either sent or refused instead of quietly ignored. Set it with `effort:` in an `llm:` block, or from the effort submenu on the [`agentPrompt`](/docs/automations/triggers/interaction.worker/elements/agentPrompt/) model picker.

- **[LLM/Providers]** Added image support to LLM chats. Images can be attached to a turn or pasted into an [agent prompt](/docs/automations/triggers/interaction.worker/elements/agentPrompt/), and they render inline in transcripts.

- **[LLM/Tools]** Agent tools can define display `labels:` (`summary:` and `active:`) and an `icon:` for transcripts, so a tool call reads as "Searching the knowledge base" rather than as a raw function name. A label can also carry placeholders, resolved against that call's own parameters, so the row reports what the agent actually asked for rather than a fixed phrase. The agent never sees either; the icon defaults to `hammer`.

- **[Platform/LLM]** Added a neutral `finish_reason` to LLM chat responses. This is what tells a truncated or interrupted turn apart from a completed one, and it's shown in the transcript viewer.

- **[LLM/Providers]** Added Qwen Cloud and z.ai as first-class [LLM providers](/docs/agents/#providers). Both appear in the provider list with their own endpoints, model hints, and brand icons.

- **[LLM/Providers]** Added [OpenRouter](/docs/agents/#providers) as a first-class LLM provider. One account reaches nearly every frontier model, and until now using it meant configuring a generic OpenAI-compatible provider: type the endpoint URL by hand, and accept that every model showed the OpenAI logo in transcripts and pickers. Selecting OpenRouter from the provider list fills that in. The bigger gain is configuration – OpenRouter publishes a context window and the accepted input types for every model it serves, so refreshing the model list on an [agent model](/docs/records/types/agent_model/) record fills in the context window and image support for whichever model you pick, across every vendor it fronts. Most providers don't report that much about their own models. Model IDs are namespaced by vendor, like `anthropic/claude-sonnet-5` or `openai/gpt-5.6-terra`, and transcripts and pickers show the OpenRouter mark rather than the underlying vendor's, since that's the route the request and the bill actually took; add a `display:` block to the model record if you'd rather see the vendor.

- **[LLM/Providers]** Updated the Claude model IDs offered by autocompletion for the Anthropic and AWS Bedrock providers.

- **[Toolbars/Search]** A [worklist](/docs/worklists/) search bar can now host an AI agent that reads, rewrites, and runs your query. Search syntax is the single hardest thing in Cerb to learn, and the cost of that lands on exactly the people least equipped to pay it – describing what you want in plain language is a large win, and it's a win everywhere a worklist appears.

- **[Automations/Interactions]** Added an [`interaction.worker.agent`](/docs/automations/triggers/interaction.worker.agent/) trigger for [automations](/docs/automations/) that drive an editor from an agent pane. `interaction.internal` exists to hide the automations Cerb runs on its own behalf – record choosers, autocomplete helpers, the dialogs inside the automation and metric builders – so you can filter them out of a worklist and never think about them again. Agent chats had been sharing that trigger for one reason: it was the only one offering [`uiCommand`](/docs/automations/triggers/interaction.worker/elements/uiCommand/), which put a worker's own conversations in the bucket meant for machinery. They now have a trigger of their own. Script autocompletion offers the element and its options, the Form Builder gives it a real inspector instead of a raw KATA box, and a toolbar's `interaction: uri:` autocompletion lists agent interactions alongside ordinary worker ones. In every other respect it's an ordinary worker [interaction](/docs/interactions/) – same form elements, same awaits, same resumable conversations.

- **[Automations/Interactions]** A parked conversation now describes itself in the lists that offer it back to you. Previously every one looked alike: the automation's own description on a generic clock icon, separated only by "Last active 18 hours ago". Ten chats with one automation produced ten identical rows, so the list was quicker to ignore than to read, and the work quietly got redone in a fresh conversation instead. A conversation now takes its name and icon from the toolbar item that launched it, and when the form shows an [`llmTranscript`](/docs/automations/triggers/interaction.worker/elements/llmTranscript/) it also picks up the model provider's mark and an excerpt of your most recent message. Rename a toolbar item and its past conversations are renamed with it. None of this needs configuring; an automation that wants something different can add an optional `resume:` block to its `await:form:` with `label:`, `preview:`, `icon:`, or `color:`. Each is sticky – a key that evaluates empty keeps what was stored rather than clearing it, so a long agent turn can't blank the name of the conversation it belongs to.

- **[Automations/Interactions]** A failed agent turn now returns to the chat instead of ending the [interaction](/docs/interactions/). Until now any failure on a background turn ended the conversation with a generic "please try again", and whatever the worker had typed was gone – including failures that clear on their own in seconds, like a rate limit that came back in a third of a second having generated nothing and billed nothing. The reason now appears above the composer, led by what to do about it and followed by the provider's own text, which is often the only thing that names the model or the region. The message is restored to the composer, so sending again is a click instead of a retyped paragraph, and the session is rewound to where it stood before Send so a resend can't leave behind a duplicate of a message the model never answered. Automation authors reach the same failure through the [`llm.agent:`](/docs/automations/commands/llm.agent/) node's `on_error:` branch, whose output var carries `error_status`, `retryable`, and `retry_prompt` for branching on the failure class.

- **[LLM/Providers/Interactions]** A rate-limited agent turn now retries itself instead of interrupting the chat. Providers with low per-minute request limits can rate limit an ordinary turn in a busy conversation, and until now that ended the turn – you had to press Send again even though nothing had been generated and the limit would clear within seconds. A rejection (429) or an overloaded provider (529) is now retried up to three times, honoring the provider's own wait when it names one and backing off 5 seconds and then 15 when it doesn't. While it waits, the conversation says why and for how long, so a pause never looks like a stalled model. Only rejections are retried, and deliberately so: those are requests a model never saw, so nothing was generated and nothing was billed. A turn that timed out is never retried, because the provider may well have produced – and charged for – a full response that we simply stopped waiting for. Rate limits from AWS Bedrock and Ollama are also reported accurately now, rather than described as the provider being unreachable.

- **[LLM/Providers]** Added response streaming to OpenAI and every OpenAI-compatible provider: OpenAI, Docker Model Runner, Gemini, Qwen, z.ai, Groq, Together AI, and Hugging Face. Until now only Anthropic streamed, so a turn that ran past the request timeout was cut off mid-generation and everything it had produced was paid for and thrown away. Streaming replaces that total time limit with an inactivity cutoff, so a turn that's actively producing output is never interrupted and only a genuinely stalled one is – and a running turn can be stopped, keeping whatever it had already written. Groq, Together AI, and Hugging Face each carried their own copy of the request logic and now share the OpenAI implementation, picking up the longer per-turn budget that background turns use along with failure classification, so a rate limit is retried rather than surfacing as an error. Streaming is on by default wherever it's supported; add `stream@bool: no` to a provider's block to turn it off, which is worth trying against an endpoint that doesn't stream correctly.

- **[LLM/Providers]** Ollama now streams responses. A streamed turn appears as it's written and the Stop button ends it mid-generation, and a turn cut short – by a stop, a dropped connection, or a worker that dies – keeps the text and completed tool calls that arrived, recorded as truncated rather than lost. Reasoning models stream their thinking alongside the reply, and token counts and the stop reason are recorded exactly as on a non-streamed turn. Because Ollama sends no keepalive while it works, the entire wait for the first token counts as silence: a local server loading a large model off disk, or Ollama Cloud queueing behind other requests, can be quiet for a long time before anything arrives. The allowance for that is generous by default and can be raised with `stream_stall_secs`.

- **[LLM/Providers]** In the Ollama provider, the Ollama Cloud API endpoint is now offered as a suggestion.

- **[LLM/Providers]** Added token usage counts to the Ollama provider, so an Ollama turn reports what it consumed in transcripts like every other provider.

- **[LLM/Providers]** [AWS Bedrock](/solutions/integrations/bedrock/) now runs on the Converse API, so every model family works rather than only Anthropic. DeepSeek, Qwen, GLM, Llama, Nova, Mistral, and others now return their reply text, token counts, and tool calls, and models that emit reasoning no longer leak it into the answer.

- **[LLM/Providers]** AWS Bedrock now streams responses. It was the last chat provider still sending one blocking request, so a turn that ran past the timeout was cut off mid-generation and everything it had produced was discarded. Streaming is used automatically on the models that support it – Bedrock reports that per model, and a model that can't stream quietly falls back to a normal request instead of failing, so nothing needs configuring either way. Prompt caching, tool calls, and separated reasoning all behave exactly as they do on a non-streamed turn.

- **[LLM/Providers]** AWS Bedrock now supports [prompt caching](/docs/agents/#long-conversations) on the models that offer it. Cerb checks your account's own model catalog to find them, so a model without caching is never sent a cache marker.

- **[LLM/Providers]** Extended thinking and reasoning effort can now be set on AWS Bedrock models. Until now a Bedrock model reasoned at whatever depth it chose, with no way to raise it, lower it, or turn it off – every other provider already read the `thinking:` block and the `effort:` key, and Bedrock ignored both, so a hard problem couldn't be given more thinking and a simple one couldn't be made cheaper. Both keys now work the way they do elsewhere: `thinking:` with `type: adaptive` on current Anthropic models or `type: enabled` on older ones, and `effort: low|medium|high|xhigh|max` for depth. On older models effort becomes a thinking budget sized to fit inside `max_tokens`, and if there's no room for a valid budget thinking is left off rather than sent as a request that would fail. These keys are for Anthropic models only, since Bedrock forwards the parameter straight to the model. Nothing is sent unless you set one, so existing configurations are unchanged, and the provider block's autocompletion now offers `thinking:`, `effort:`, and `stream@bool:`.

- **[LLM/Providers]** AWS Bedrock now lists its available models when you create an [agent model](/docs/records/types/agent_model/) record. The list comes from your account's own Bedrock catalog and includes the cross-region inference profile IDs that most current Claude and Nova models require.

- **[LLM/Providers]** When adding an [agent model](/docs/records/types/agent_model/) record, providers now suggest API endpoints as you type. This is particularly useful on AWS Bedrock, which uses regional endpoints.

- **[LLM/Providers]** When listing models fails, the provider's own error message is now shown instead of a bare HTTP status code. On AWS Bedrock this names the exact IAM action that's missing.

- **[LLM/Providers]** Long agent turns no longer time out after 30 seconds on Ollama, Groq, Hugging Face, Together AI, or AWS Bedrock. Every provider now honors the extended per-turn timeout that background turns allow, which previously only Anthropic and OpenAI did.

- **[Agent/Terminal]** An agent can now ask Cerb about itself, through a `cerb` command line in its [terminal](/docs/agents/#filesystem-commands). Ask an agent for "Kina's open tickets" and it has to know that `ticket` is a record type here, that `status` and `owner.at` are things you can filter by, and that your custom fields exist at all – none of which is in its training data, and none of which is a file anyone would think to import, so until now an agent guessed, and a wrong guess looks exactly like a working one until the query returns nothing.

- **[Agent/Pane]** An AI agent chat now gets its host editor's commands as tools automatically. Until now a chat that drove an editor had to carry the whole bridge itself – a `tool/` definition per command plus an [`on_tool:`](/docs/automations/triggers/interaction.worker.agent/) branch with a [`uiCommand`](/docs/automations/triggers/interaction.worker/elements/uiCommand/) await to dispatch each one – which made a chat for the automation editor 279 lines before you wrote a word of your own, and which went stale silently when the editor gained a command afterwards.

- **[Agent/Pane]** An agent pane can now answer a tool on the server, with no round-trip to the browser. Every tool an agent pane gave a chat used to be a question for the editor – read this field, write that one – which is the right shape when the answer is in the document in front of you, and the wrong one when the answer belongs to the installation itself. The [Icon Builder](/docs/setup/developers/icon-builder/)'s assistant is the case that made it obvious: naming an existing icon is most of the work, and the browser has no way to say what the set contains. It now gets a `cerb_list_icons` tool answered on the server, returning every icon name in the set, narrowable with a filter when the list is long, so the assistant matches an existing icon instead of guessing whether one exists.

- **[Agent/Pane]** The command bar can now host an AI agent chat. Every agent pane so far has sat beside an editor, with the job of reading and writing the document in front of you, which left nowhere to put a chat that follows you around the app instead of belonging to one screen. A chat written for the command bar gets two things an editor chat has no use for: `cerb_get_page` reads the page Cerb actually routed, which is what you're looking at even when the browser URL says otherwise, and `cerb_open_search` puts a search popup for any record type in front of you, prefilled with a query the agent wrote – better than describing a query and asking you to paste it. Both are one-way on purpose. The command bar can put something in front of you but can't read anything back, so a chat there tells you what it searched for and lets you read the results; it never sees them itself, and it knows where you are but never what's on the screen. Which agents the command bar offers is set on each agent, the same way every other surface is, and the command bar's existing non-agentic shortcuts are untouched.

- **[Agent/Chat]** An agent chat in an [agent pane](/docs/toolbars/interactions/agent.pane/) now follows the newest turn, and holds its place when you scroll up to read. Following the newest turn is right until you scroll up to re-read something, and then it's exactly wrong: every poll tick yanked you back to the bottom mid-sentence, and a long agent run was the worst case because the ticks never stop. The transcript now pins to the bottom only when you were already there, including across the re-render that each step of a tool loop causes, so reading something is no longer a race against the next turn. When there's newer content below you, a "Jump to latest" pill appears; clicking it takes you down and re-arms the follow. Sending a message re-arms it too, since nobody scrolls up in order to miss their own reply.

- **[LLM/Providers/OpenAI]** [Agent models](/docs/records/types/agent_model/) pointed at OpenAI's own API now use the `/v1/responses` endpoint, where tools and reasoning work together. The older `/v1/chat/completions` endpoint refuses function tools on a reasoning turn for gpt-5.4 and newer, which costs a tool-using agent its reasoning in the one configuration where it matters most. That endpoint also returns reasoning summaries, which is the only way an OpenAI model shows its thinking; it's authored as `thinking: display:` – the same block and keys as Anthropic's, so it reads the same across providers – and it's on by default for a model flagged as thinking. Any other endpoint keeps using `/v1/chat/completions`: Azure, llama.cpp, vLLM, MLX, and every OpenAI-compatible provider. Set `api: chat` on an OpenAI record to pin it to that endpoint, and `api: responses` is refused on an endpoint that can't serve it rather than quietly downgraded.

- **[LLM/Providers/OpenAI]** LLM providers using an OpenAI-compatible API can now pass arbitrary `extra_body:` parameters through to the inference server. The OpenAI-compatible ecosystem puts its knobs somewhere other than where the OpenAI spec does, and a fixed set of typed parameters can't keep up – Apple-silicon oMLX serving Qwen3 forwards `chat_template_kwargs` to the Jinja template but doesn't map the standard top-level `reasoning_effort` into it, so `effort:` reached the server, was dropped on the floor, and nothing said so. llama.cpp, vLLM, SGLang, and unsloth all have their own such keys. The key is named and shaped after the OpenAI SDK's own `extra_body`, deliberately, so a snippet from a server's documentation transcribes straight into [KATA](/docs/kata/): the _contents_ merge into the top level of the request body, so `extra_body: chat_template_kwargs: reasoning_effort: medium` puts `chat_template_kwargs` on the wire rather than a key called `extra_body`. Cerb keeps ownership of the request's structure, so `model`, `messages`, `stream`, `stream_options`, and `tools` can't be overwritten.

- **[LLM/Agents/Performance]** An agent's system prompt is composed once and frozen for the life of the conversation, so the most cacheable part of every request stops moving. It's rebuilt when someone _edits_ the [automation](/docs/automations/) – the authored `system_prompt:`, `tools:`, `mounts:`, or `terminal:` block – and that takes effect on the worker's next message. Nothing else rebuilds it: a host gaining a tool, or an agent writing a file into a volume it can write to, leaves an open conversation's prompt alone. The session now stores the full prompt that was sent rather than the author's fragment, so a [transcript](/docs/automations/triggers/interaction.worker/elements/llmTranscript/) can answer what the agent actually saw. A trigger may contribute the opening of that prompt, the same way it already contributes tools, and the author's own `system_prompt:` is appended to it rather than replacing it.

- **[Agent/Terminal]** An agent can now ask Cerb about the installation it's running in, through a `cerb platform` command line in its [terminal](/docs/agents/#filesystem-commands). The documentation describes the plugins that exist; it can't tell an agent which of them are in your installation, which are switched off, or what a third party added. Ask an agent whether it can file a JIRA issue, or which automation triggers it may write for, and until now it either guessed or told you to go look.

- **[Agent/Terminal]** An agent can now validate [KATA](/docs/kata/) and JSON before it saves them, through a `cerb code` command line in its [terminal](/docs/agents/#filesystem-commands). A model writing an [automation](/docs/automations/) has no feedback loop: it writes the whole thing, saves, and learns from a save error what one line got wrong – then rewrites the whole thing, because it can't tell which parts were fine. That's several turns and a lot of guessing for what a linter answers in one.

- **[Agent/Terminal]** The [agent terminal](/docs/agents/#filesystem-commands)'s `search` can now tell you which words are worth searching for. `search --terms` counts how many files contain _each_ word instead of searching for all of them, so an agent can throw a dozen synonyms at a volume in one call, keep the winner, and refine – rather than guessing a query at a time. Prefix a word with `+` to require it and count the others alongside it, which collapses the numbers fast and shows what actually co-occurs. A wildcard or stem term lists the concrete words it covers, so `auto*` reports `automations (476) automation (374) automatically (228) ...`, which is how you learn the vocabulary a corpus actually uses instead of guessing at it.

- **[Agent/Terminal]** An [agent terminal](/docs/agents/#filesystem-commands) `search` that matches nothing now answers with per-word counts rather than "No matches". `search` is AND – every word must appear in the same file – so a pile of near-synonyms reliably matched nothing, and the reply gave no hint of which word emptied it. The fallback prints the same table `search --terms` gives, naming the word that matched nothing and the ones worth keeping. It keeps any `+` already in the query, so the second step of a search loop doesn't throw away the term you just established.

- **[Agents/Filesystems]** [Agent filesystems](/docs/records/types/agent_filesystem/) can now ship with Cerb and import themselves on update, so a bundled volume automatically stays current for the version you're running. It lives in the source tree as ordinary files and is imported on `/update`, so an agent has reference material without anyone uploading an archive. Each volume carries a manifest and only its hash is read at runtime: an update where nothing changed costs one registry read and does no work at all, while a changed volume is zipped and run through the same import job an admin upload uses, inheriting its batching, retry, prune, and [queue job](/docs/records/types/queue_job/) progress. The job is drained inline, so when `/update` finishes the content is there. A bundled volume _mirrors_ what shipped – a file created in it by a worker or an agent is removed on the next update – while content imported by hand through the ordinary upload is never touched. **Setup » Developers » Platform** gains a 'Reload' button that reconciles every bundled volume against its rows without waiting for a version change.

- **[Agents/Filesystems]** Cerb now ships a skills volume for its own AI agents. The bundled `cerb-agents` [filesystem](/docs/records/types/agent_filesystem/) carries ten skills – the agent terminal, KATA, automations, scripting, search queries, records, data queries, icons, mail replies, and the documentation – each one file an agent reads when it needs it. An agent can look up the grammar of a search filter or the shape of an automation command instead of guessing, which is where a capable model is most often subtly wrong.

- **[Agents/Filesystems]** Cerb now ships its own documentation as a bundled [agent filesystem](/docs/records/types/agent_filesystem/). The `cerb-docs` volume carries the complete documentation as Markdown – the reference manual, [guides](/guides/), worked [solutions](/solutions/), [tips](/tips/), [workflows](/docs/workflows/), and release notes – and imports itself on update like any other bundled volume.

- **[Agent/Pane]** An [agent pane](/docs/toolbars/interactions/agent.pane/)'s role and tool inventory are composed by Cerb at runtime. An agent sitting beside an editor is told what it is, where it sits, and what that editor can do, with nothing in the [automation](/docs/automations/) that drives it. The author's own `system_prompt:` is appended to that rather than replacing it, so adding a line about a custom tool is one line, and leaving it empty – the normal case – still produces a complete prompt. Composing at runtime rather than generating into each script is what lets an improved role reach an automation that was deployed before it: nothing is patched and nothing is regenerated. The tool inventory beneath each role is built from the live catalog, so it can't drift from the tools actually offered, and each agent-pane component names the skills its work needs and the documentation paths that cover it. Both pointers are emitted only when the volume behind them is really mounted – a chat can be authored with no filesystem at all, and sending an agent after files it can't read is worse than saying nothing.

- **[Agents/Files]** Added bulk update for [agent files](/docs/records/types/agent_file/). The agent files worklist has a bulk update button for moving files between [filesystems](/docs/records/types/agent_filesystem/), editing their fields, and running automations over a batch. The popup also lists any [`record.bulkUpdate`](/docs/automations/triggers/record.bulkUpdate/) automations bound to agent files, so a batch can be handed to a script – generating embeddings for every file on a volume, for instance. Moving a batch to another filesystem skips any file whose path is already taken on the destination, since one filesystem can't hold two files at the same path; the rest of the batch still moves. Bulk updating agent files requires an administrator, matching the rest of agent file editing.

- **[AI/Agents]** An [AI worker](/docs/agents/)'s peek has an **AI** tab for setting what the agent brings to a turn and where it runs – instructions, which models it may use, [filesystems](/docs/records/types/agent_filesystem/), tools, and its [`cerb` command line](/docs/agents/#the-cerb-command-line). A rail lists **Everywhere** first and then each surface the agent can run on, with a green dot beside the ones it's turned on for. 'Everywhere' is what the agent brings no matter where it's running, and a surface _adds_ to that rather than replacing it: filesystems, tools, and command-line namespaces are the union of the two, and only the model query and the chat it runs are swapped outright.

- **[AI/Agents]** Cerb now ships the **chat an agent runs by default**. The `cerb.ai.agent` [workflow](/docs/workflows/) installs an [`interaction.worker.agent`](/docs/automations/triggers/interaction.worker.agent/) automation named `cerb.ai.agent.chat`, and an [agent](/docs/agents/) that names no chat of its own runs that one – so creating an [AI worker](/docs/agents/) and turning it on for a surface is all it takes to have a working conversation there.

- **[AI/Agents]** Added **[Agent Tool](/docs/records/types/agent_tool/)** records – a record type for the tools an AI agent can call. A tool is defined once and then added to any agent, rather than restated in each one. The record wraps an [`agent.tool`](/docs/automations/triggers/agent.tool/) [automation](/docs/automations/) with everything the automation itself has nowhere to say: the name the model calls, the description it reads, and the icon and wording its transcript shows. The automation knows how to do the work; the record says what the model should call it and what the conversation shows while it runs.

- **[AI/Agents]** Agents can now call the tools you define, referenced by name from an agent's own configuration or from a chat's `tools:` block. A reference is just the [agent tool](/docs/records/types/agent_tool/) record's name, and the entry under it may override the presentation the record supplies – `description:`, `icon:`, and `labels:` – or switch the tool off for this agent with `disabled@bool: yes`. A conversation's tools are settled when it starts, because the tool set sits in the prompt prefix the provider caches: editing a tool reaches new conversations rather than rewriting one already under way, and switching a tool off refuses new calls to it rather than making it vanish mid-conversation. A tool that's disabled, or whose record is missing, when a conversation _starts_ is never offered at all, so the model is never shown something it would only be refused.

- **[Automations/Agents]** Added an [`agent.tool`](/docs/automations/triggers/agent.tool/) trigger for the [automation](/docs/automations/) behind an [agent tool](/docs/records/types/agent_tool/) record. It's handed the environment of the call rather than only the model's arguments, so a tool can refuse work that doesn't belong where it was invoked. The arguments arrive as `inputs.*`, declared in the automation's own `inputs:` block – that block _is_ the schema the model is shown, so a tool is self-documenting and there's exactly one place to change what it takes.

- **[AI/Agents/Transcripts]** An agent chat can now show who is speaking instead of a generic "Agent". An [`llmTranscript:`](/docs/automations/triggers/interaction.worker/elements/llmTranscript/) element takes an `agent:` block, and every agent turn is attributed to it: the byline reads the agent's name and the avatar is the agent's rather than the vendor's. The model stays visible – its mark moves to a small badge on the lower right of the avatar, in the provider's brand color – so a reader can see who they're talking to and still see that it's an AI, which one glyph alone couldn't say.

- **[Setup/Developers]** **LLM Agent Transcripts** now identify the agent behind each session. A transcript is titled by its agent, an **Agent** chip links to the record holding the instructions and tools the turns were composed from, and every agent turn carries that agent's picture and byline instead of a generic "Agent". The session uuid stops being the headline: only its leading characters distinguish one session from another, so it's quoted like a git commit – eight characters in the eyebrow, the whole value on hover and on the **Permalink** button. That leaves the list showing what you actually pick a transcript by – which agent ran it, for whom, how long ago, and how large it got.

- **[AI/Agents]** Agents appear in the command bar under their `@handle`, over a line saying what picking one does. The bar mixes agents with every other shortcut in Cerb, so a row reads as the agent you'd `@mention` anywhere else rather than as the name of the script behind it.

- **[Agent/Terminal]** Added `cerb platform version` to the [`cerb` command line](/docs/agents/#the-cerb-command-line). An agent can ask what version of Cerb it's working in, whether that install is self-hosted or on Cerb Cloud, and what PHP and database it runs on. It reports Cerb's version and build, the deployment, the Devblocks platform build, PHP with its SAPI, and the database server's own version string, which names the flavor too. This is what an agent should ask before assuming a feature exists: `version` is the exact string a [workflow](/docs/workflows/)'s `cerb_version: '>=12.0'` gate or a [package](/docs/packages/)'s `requires.cerb_version` compares against, while `build` is a date serial that moves with every release and is what the updater compares – it isn't a version and doesn't sort against one. The deployment row reads **Cerb Cloud** when Cerb hosts the install, naming its subdomain, and **Self-Hosted** otherwise. Like the other sub-commands it takes `--format json` and binds its rows for piping.

- **[Records/Workers]** On [worker](/docs/records/types/worker/) worklists, AI accounts now carry a visual `bot` indicator, so an agent is recognizable at a glance in a roster of people.

- **[AI/Agents/Mail Routing]** An [agent](/docs/agents/) can now sit beside both mail routing editors – the standalone **Mail Routing Rule** record and a group's **Mail: Incoming** tab – reading and writing the rules and testing them against a sample message. It's one surface rather than two, because the grammar, the schema, and the evaluator are shared; what differs is where in the pipeline the document runs, and the agent is told that when it reads: `scope` comes back as `rule` for a standalone rule that decides the **group**, or `group` for a group's own rules that decide the **bucket**.

- **[Records/Workers]** An AI worker's whole [agent](/docs/agents/) configuration can now be set through the [records API](/docs/api/) and [workflows](/docs/workflows/), as an `agent_config` field on the [worker](/docs/records/types/worker/) record. Until now the **AI** tab was the only way to author one, which left agents out of the text-based tooling every other record type already has – an agent couldn't be version-controlled, diffed, or synchronized between a development and a production install. Write it as a nested [KATA](/docs/kata/) object, so a workflow template can target a single leaf – a `models_query:` drawn from workflow config, say – instead of interpolating into one opaque blob; a KATA string is accepted too for anyone writing it by hand. Either way it's validated against the same agent schema the AI tab uses, so a malformed configuration is refused rather than stored. It's only meaningful on a worker with `is_ai` set.

Picking one seeds a working trigger, script, and policy; several ask a few questions first and generate the script from your answers. The five bundled templates cover AI agent chats and agent tools, worker interactions, reacting to ticket changes, and sending a Slack message. - **[Automations/Scripting]** In automation scripting, a new [`|number_pretty`](/docs/scripting/filters/#number_pretty) filter formats large numbers in a human-friendly form – `{{12345678|number_pretty(1)}}` reads as `12.3M`. - **[Automations/Scripting]** In automation scripting, new [`|bin2hex`](/docs/scripting/filters/#bin2hex) and [`|hex2bin`](/docs/scripting/filters/#hex2bin) filters convert between a binary string and its hexadecimal representation. - **[KATA/Automations]** Converting a dictionary to [KATA](/docs/kata/) with [`|kata_encode`](/docs/scripting/filters/#kata_encode) now annotates decimal numbers with [`@float`](/docs/kata/#float), so they read back as numbers rather than text. A script that encoded `1.5` and read it back got text it couldn't do arithmetic on without converting first. Whole numbers already survived this round trip and decimals did not.

- **[Queues]** [Queues](/docs/queues/) can now configure a retry policy – a maximum number of retries and a retry window – using exponential backoff so each successive failure waits longer. - **[Platform/Storage/Queues]** Added a `cerb.storage.migrations` [queue](/docs/queues/) covering the whole lifecycle of storage objects – migrations, archival, and deletions. - **[Platform/Storage/Queues]** Storage schema deletions are now handled by the `cerb.storage.migrations` background queue rather than the `devblocks_storage_queue_delete` table, and existing rows are migrated to the queue on upgrade. This wasn't used by the 'disk' and 'database' storage engines, but it is by 's3'.

- **[Queues]** [Queues](/docs/queues/) now have a configurable 'claim window' – the amount of time a consumer is granted to process a message it has claimed. If a message stays in flight longer than that, the stalled claim is released and the message is either failed or retried, which handles a consumer that dies unexpectedly instead of leaving work stuck forever.

- **[Queues]** Background work now runs in **lanes**, so a queue of AI agent turns can no longer take every concurrency slot. Slots are split into a fast lane, a slow lane, and a commons that either may use. Work that holds a slot for as long as a model takes to answer – an agent turn, a [scheduler](/docs/setup/configure/scheduler/) job that runs in parallel – draws from the slow lane; work that yields every batch – a bulk update, an import, an export – draws from the fast one. Neither can take the other's dedicated slots, and half the pool stays shared, so an idle install still gives any single job everything it can use. The axis is how long a slot is _held_, not how important the work is. A three-slot install gets one slot per lane and one shared; below three there's nothing to divide and every slot is shared. Nothing about this is configured – a job names a lane in code and gets back a slot or nothing, and the split follows the pool size.

- **[Queues/Scheduler]** The per-job **'runs in parallel up to'** setting is gone from **Setup » Configure » [Scheduler](/docs/setup/configure/scheduler/)**. There's nothing left to tune: a parallel job takes a slot from the slow lane like any other long-running drain, and drains as fast as it can. A concurrent job's row now counts down on a real timer instead of showing a static "continuous" label – though it stays out of the page's **next to fire** chip, since a job that drains as fast as it can has no cadence to be next on. **Run now** on a parallel job takes a real slot – so it answers "All concurrency slots are busy. Try again in a moment." rather than starting work that has nowhere to run.

- **[Queues/LLM]** A single background worker now runs several [agent](/docs/agents/) turns at once, so a queue of waiting turns finishes in about the time of its slowest instead of the sum of all of them. An agent turn spends nearly all of its life waiting on the model provider, so a worker holding one turn sits idle for almost all of it. A worker now carries several turns together, taking the next queued turn as each one finishes, for as long as its admission window is open – and every turn admitted still gets its full time budget, since the window decides whether another turn _starts_, never whether one finishes. One conversation still advances a single turn at a time across every worker on the install: resuming the same chat in two tabs, on two devices, or from an unattended agent can no longer interleave two replies into it, because a worker that finds a conversation already advancing puts its message back and runs it once the conversation is free, without counting that as a failed attempt. There's no configuration option; the count follows the license.

- **[Setup/Queues]** Added a **Setup » Configure » Queues** page: what the concurrency pool is divided into, and what's running in it right now. **Setup » Subscription** answers how much capacity you have; this answers what it's doing. The split is drawn one block per slot on two rows, **Batch jobs** and **Agent turns**, so you can see which slots each kind of work holds and which ones both may use – and it's drawn from the same component the Subscription page uses, so the two can't come to disagree about the shape of the pool.

### Search indexes

https://www.youtube.com/embed/a2IhZPPLWls

- **[Search/Records]** Added a [Search Index](/docs/records/types/search_index/) record type. Each index manages a linked custom [search filter](/docs/search/) on any record type. New search index extensions can be implemented with [plugins](/docs/plugins/) (e.g., TF-IDF, BM25, vector embeddings, Elasticsearch, Qdrant, Pinecone).

- **[Search/Full-Text]** Implemented a local full-text [search index](/docs/records/types/search_index/) extension that is optimized for performance and intended to replace MySQL's hard-to-scale FULLTEXT indexes. For each index, a record type, filter query, and content template are configurable. This makes it simple to create custom search indexes on only the content you care about; for instance, a set of custom fields on the past 3 years of tickets. Cerb will automatically manage these constraints to keep the index updated. Each search index adds a new [`filter:`](/docs/search/#search-indexes) to worklists of that record type. When a search index has priority zero it overrides the default filter when a search query has no explicit filters.

- **[Search/Full-Text/Developers]** Technical notes. The new local full-text search index extension splits tokens on spaces and punctuation but allows dashes and dots within terms (e.g., hostnames, email addresses, IPs, ticket masks). This significantly improves search performance because these terms can be matched directly without a phrase search. Tokens are stored as xxHash 64-bit signed integers, so each is a fixed 8 bytes regardless of length. Token hashes are consistent across all Cerb environments. Lookups are O(1). Distinct tokens are linked to record IDs with a precached term frequency for quick TF-IDF/BM25 scoring. Queries sort 'AND' terms by the lowest document frequency first and JOIN in that order to significantly reduce lookups. Since indexes are now managed by Cerb and not MySQL, indexes can be analyzed, pruned, merged, split, sharded, etc.

- **[Search/Records]** On all record types, the default search filter is now configurable when no explicit `filter:` is given by setting the priority of the [search index](/docs/records/types/search_index/) to zero. For instance, default queries can route to a custom search index for a specific set of custom fields rather than just the record name (e.g., part number lookup). With any other priority, custom search filters will be sorted to the top of query autocompletion suggestions.

- **[Search/Full-Text]** Added [wildcard support](/docs/search/#search-indexes) to custom search indexes with asterisk (`*`). This matches tokens in the vocabulary using OR for that term. For instance: `11.1* release*` to match `11.1.6 released` and `11.1 release`.

- **[Search/Full-Text]** Added [stemming support](/docs/search/#search-indexes) to custom search indexes with a tilde suffix (`~`). This fuzzy matches tokens in the vocabulary using OR. For instance: `automate~` expands to: automate, automates, automation, automating, automated.

- **[Search/Full-Text]** Added support for [excluded terms](/docs/search/#search-indexes) in custom search index queries by prefixing a term with a dash (`-`). At least one included term is still required. For example, `workflow -automation` matches documents that contain `workflow` while excluding any that also contain `automation`.

- **[Search/Full-Text]** [Search index](/docs/records/types/search_index/) filters send additional parameters through to extensions. For instance, `top:10` for ranked results.

- **[Search/Full-Text]** Added support for [`top:`](/docs/search/#search-indexes) parameter to limit and rank results by score in full-text search queries.

- **[Search/Full-Text]** Added support for boosting TF-IDF scores using custom templates in full-text [search indexes](/docs/records/types/search_index/). This gives more relevancy to document titles, etc.

- **[Search/Scheduler]** Updated the `search` scheduler job to handle custom [search indexes](/docs/records/types/search_index/).

- **[Search/Queues]** [Search index](/docs/records/types/search_index/) cards now display indexing progress and have a re-index option to launch a background [queue job](/docs/records/types/queue_job/).

- **[Search]** Added **search facets** – named subsets of a record type. Some useful views are a filtered slice of an existing record type rather than a type of their own; [AI workers](/docs/workers/) are the obvious case, since they're workers but "Workers" isn't where you'd look for them. A facet gives that slice its own name, icon, and Search menu entry with its filter always applied, and sits beside the real record types rather than nested in a submenu. Each facet keeps its own columns and sort, so customizing it doesn't disturb the parent type's search.

- **[Metrics/Search]** Added a [`cerb.search.index.records`](/docs/metrics/) gauge metric for counting records over time per [search index](/docs/records/types/search_index/) and engine.

- **[Platform/Search]** Added on-demand search re-indexing for specific records. A record can be made searchable immediately after it's written rather than waiting for the next scheduler sweep, so a newly created record is findable right away. Bulk writers – ZIP imports, re-indexes, and bundled filesystem syncs – index in batches instead, so a thousand-file import doesn't reindex a thousand times.

- **[Cerb UI/Rating]** Added a `CerbUI.Rating` component for ordinal ratings, drawn as a row of repeated glyphs filled from the left up to the selected value. The host owns the glyph and the scale and the component only paints state and reports the value, so any [icon](/docs/developers/icons/) works and the same control reads as stars, brains, locks, or coins depending on what's being rated. Hovering previews the value you would set – repainting the glyphs and live-updating the tier label beside them – and moving off the control restores both to what's stored. A meter is the read-only twin of the rating control – the same 1-of-N read, sized for a worklist cell, a menu row, or a property grid. - **[Cerb UI/RecordChooser/ValuePicker]** A `CerbUI.RecordChooser` or `CerbUI.ValuePicker` can now show values it doesn't own – an inherited set, a grant that comes from somewhere else – as faded "ghost" tiles sitting alongside your own selections. What it answers is "what do I already have here?", in the one place you're looking while you decide what to add. That question used to be answered by a placeholder, which only works while a field is _empty_ – it disappears the moment you add anything, which is exactly when you most need to see what you're adding to. A ghosted value is also dropped from the field's own menu, so you can't add the same thing twice. Ghosts are managed by the page rather than by the field, because what they stand for lives somewhere else on the form, so a field can follow an edit made elsewhere without being rebuilt. Both components are documented in **Setup » Developers » UI Reference** with a live example each: two fields side by side where the left one grants and the right one adds to it.

- **[Packages/Library]** A [package](/docs/packages/)'s `image` can now name the colors its icon is painted in, so a package tile in the library, and in the Add-tab and Add-widget choosers, can match the thing it installs. A `library.image` is either an embedded `data:` image or a space-delimited art spec whose first word is a Cerb icon name and whose optional second and third are the background and glyph colors as `#rgb` or `#rrggbb`. Writing `todo` gives the icon on a neutral gray, `todo #7f7f7f` sets the background, and `todo #7f7f7f #ffffff` sets both. Either color can be a `light:dark` pair, so `todo #eeeeee:#333333` paints one color in the light theme and the other in dark, and a color with no pair is used in both. The word `auto` holds a slot at its default, which is how you set a foreground without pinning a background: `todo auto #d62728`. Anything unusable falls back on its own slot's default, so an unrecognized icon name still lets your colors through and a malformed color still lets your icon through.

A role also exposes `_image_url` now, so its avatar turns up wherever Cerb draws a record's image: placeholders, mention chips, custom field forms, comments, and role autocomplete entries.

- **[Automations/KATA]** In [KATA](/docs/kata/), a `type/name:` name that becomes a dictionary key must now be a valid variable name – letters, numbers, and underscores only. Previously a name containing a dash silently rendered as `0` wherever it was read back, because `{{a-b}}` is the subtraction `a - b` rather than a variable reference. This caused quiet failures like a worklist export column full of zeros, or a snippet placeholder that evaluated to nothing. The check is applied where a name actually lands in a dictionary – `inputs:`, `await:form:elements:`, snippet and dashboard prompts, worklist export columns, and LLM tool `parameters:` – and is available declaratively as `nameFormat: variable`. The parser still allows the wider character set elsewhere, since most names are labels or handles that are never read back as placeholders.

- **[KATA]** In [KATA](/docs/kata/), the [`@float`](/docs/kata/#float) annotation now accepts a multiple-line indented value like the other annotations. Following a `@float` key with an indented block was a syntax error, and leaving its value blank produced an empty object rather than a number.

- **[Security/Dependencies]** Upgraded `phpunit/phpunit` to v12.5.33 in response to a security advisory.

- **[OAuth/Security]** OAuth2 consent is now bound to the app and the scopes it was granted for. Login state is reused for 20 minutes, and in the OAuth flow it was only cleared once an authorization request ran to completion – so a flow abandoned after the consent screen, where a worker approves an app but the browser never makes it back to `/oauth/authorize`, left a granted consent sitting in the session. Within that window, following an authorization link for a _second_ app issued it an authorization code with no consent screen shown at all, and the same gap let an app that had already been approved widen its scopes silently. The login state now records the `client_id` and the scope set that were actually displayed on the consent screen, and `/oauth/authorize` requires both to match the request in hand. Scope comparison ignores order and duplicates, so a reordered scope list doesn't force a redundant re-prompt. A declined request still counts as answered and continues to return `access_denied` to the client rather than looping back to the consent screen, and a POST to `/login/consent` with no authorization request pending now grants nothing.

- **[OAuth Apps/Security]** The OAuth2 authorization flow now returns to the hostname in `APP_HOSTNAME` after a worker signs in or grants consent. When an authorization request reached `/oauth/authorize` and the worker still had to sign in or approve the requested scopes, Cerb saved the return address using the hostname from the incoming request instead of the configured one. Where a proxy or load balancer presents a hostname other than the one workers browse, the round trip came back on the wrong origin – and since session cookies are scoped to a single hostname, no session existed there, so the flow either looped back to the sign-in form or stopped with an access denied error. On Cerb Cloud this showed up as a custom domain falling back to the instance's `*.cerb.me` address partway through.

- **[Security/LDAP/SSO]** Added CA certificate and certificate-verification options for LDAPS. A directory using a self-signed or private CA can now be connected by supplying its CA certificate to Cerb, rather than modifying the system-wide TLS configuration.

- **[Security/Dependencies]** Upgraded `twig` to v3.26.0 in response to a security advisory.

- **[Security/SSO/OIDC]** Hardened the OpenID Connect SSO callback to validate the OAuth `state` parameter against a per-request value stored at the start of the authorization request. Previously an attacker could deliver a `?code=...&state=...` URL to a victim and force their browser through the callback, signing them into the attacker's identity (login CSRF / session injection). Mismatches now abort with `auth.failed`.

- **[Security/SSO/OIDC]** Hardened the OpenID Connect SSO flow by sending and verifying a per-request `nonce` (OIDC Core §3.1.2.1, §3.1.3.7). The authorization request now includes a 128-bit random nonce that is persisted in the session and constant-time compared against the ID token's `nonce` claim. This prevents ID-token replay across sessions and devices and brings the implementation into spec compliance for the authorization code flow.

- **[Security/SSO/OIDC]** Hardened the OpenID Connect SSO flow by rejecting ID tokens whose `email_verified` claim is present and not strictly `true` (OIDC Core §5.1). Without this check, an IdP that allows users to set arbitrary unverified email addresses could let an attacker impersonate any worker by claiming their email. The check passes through when the claim is absent to preserve compatibility with custom IdPs that don't emit it.

- **[Security/SSO/OIDC]** Hardened OpenID Connect ID-token signature verification when the IdP omits the `kid` (Key ID) header. Previously the code validated against only the first JWK in the JWKS, which silently failed if the JWKS contained multiple keys (e.g. during key rotation) and the signer wasn't first. The kid-less branch now iterates through every JWK and uses the one whose `SignedWith` constraint validates the token; if none match, a specific "did not validate against any JWKS key" error is surfaced. IdPs that emit `kid` continue to use the exact-key lookup unchanged.

- **[Security/SSO/SAML]** Closed an open-redirect path through SAML SSO. The callback was pushing `RelayState` directly into the post-login redirect stack without origin validation, so a malicious or compromised IdP (or a forged callback POST) could pin an absolute attacker URL and hijack the user post-auth. Redirect URIs are now restricted to relative paths or absolute URLs whose scheme, host, and port match the configured base URL. Same-origin absolute URLs (e.g. the OAuth2 server `/oauth/authorize` round-trip) continue to work.

- **[Security/Auth]** Switched the remaining secret-vs-secret comparisons across the codebase to `hash_equals()` so comparisons are constant-time and don't leak secrets one byte at a time. Sites updated: the centralized CSRF token check, the Support Center CSRF check, the REST API HMAC signature compare, the OAuth2 server `client_secret` verification, the worker password recovery code and secret-question answer compares, the `APP_SERVICE_TOKEN` compare, and the portal image HMAC compare.

- **[Security/Auth]** Tightened login-state hygiene so abandoned authentication flows can't bleed into the next attempt. `clearAuthState()` now also resets `motd` so a previous attempt's `worker.authenticated` automation result doesn't surface on the next login form. The redirect URI stack is cleared at the two true abandonment points: when the MFA retry limit is exceeded, and when password recovery wrong-guesses are exhausted.

- **[Security/Recovery]** When a worker completes the password recovery flow, all of their existing sessions are now evicted immediately after the password is rewritten. Previously a stolen session cookie would keep working until natural expiration even after the legitimate user reset their password specifically to evict the attacker. The eviction fires only after every gate of the recovery flow has passed (email control via the recovery code, second factor via TOTP or secret questions, and the password rewrite).
